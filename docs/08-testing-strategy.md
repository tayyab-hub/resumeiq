# ResumeIQ — Testing Strategy

> Phase 1 deliverable. Tests are written alongside each phase, not batched at the end.
> Phase 13 is a consolidation and audit pass, not the first time tests appear.

---

## 1. Shape of the test suite

```
        ╱  E2E / manual checklist  ╲      few — the 12-page manual pass
       ╱   API integration tests    ╲     ~40 — every endpoint, every error code
      ╱  Frontend component tests    ╲    ~25 — states, forms, accessibility
     ╱      Backend unit tests        ╲   ~100 — analyzers, scorer, security
    ╱__________________________________╲
```

The base is intentionally heavy on **analyzer unit tests**, because the analyzers are pure
functions: a test is a string in and an assertion out, with no fixtures, no database, and no
mocks. That property is why `analyzers/` was separated from `services/` in the architecture,
and it is what makes 80 % coverage on the interesting code achievable in 30 days.

**Coverage targets:** `analyzers/`, `services/`, `security/` ≥ 80 % line coverage — these hold
the logic worth trusting. `api/` is covered by integration tests rather than a percentage
gate. `models/` and `schemas/` are declarations and are not chased for coverage.

## 2. Backend unit tests

### `analyzers/pdf_extractor` (Phase 5)
| Test | Asserts |
|---|---|
| Valid text PDF | Text extracted, length > 200 |
| Image-only PDF | Raises `NoTextLayerError` |
| Corrupted bytes | Raises `CorruptPdfError`, not a bare exception |
| Encrypted PDF | Raises `EncryptedPdfError` |
| Zero bytes | Raises `EmptyFileError` |
| Non-PDF bytes with `.pdf` name | Raises `InvalidFileTypeError` on the magic-byte check |
| Whitespace normalisation | Runs of spaces collapse; paragraph breaks survive |
| Hyphen rejoin | `develop-\nment` → `development` |
| Bullet normalisation | `•`, `▪`, `*`, `-` → one marker |
| Temp-file cleanup | Temp dir empty after both success and exception paths |

Fixtures: 6 small PDFs generated by a script committed to `tests/fixtures/`, so they are
reproducible and contain no personal data.

### `analyzers/section_detector` (Phase 6)
Each of the nine sections detected from its canonical heading and from two synonyms;
lowercase and ALL-CAPS headings; contact detected from an email pattern with no heading;
absent section reports `detected: false`; a résumé with no recognisable headings returns nine
rows rather than an empty list; the matched heading is returned for UI explanation.

### `analyzers/statement_analyzer` (Phase 6)
"Responsible for maintaining the company website" → `GENERIC_PHRASING`, `NO_ACTION_VERB`,
`NO_METRIC`. "Reduced page load time by 40% by adding lazy-loading" → no findings, counted as
measurable. A 40-word bullet → `TOO_LONG` with its word count. "was managed by" → `PASSIVE`.
A phrase repeated 3× → one `REPETITION` finding listing occurrences. Action-verb rate is
computed correctly on a mixed résumé. **A suggestion never contains a digit that was not in
the source bullet** — this is the anti-fabrication guarantee, tested directly.

### `analyzers/skill_extractor` and `jd_parser` (Phase 7)
Alias resolution (`postgres`/`Postgres`/`PostgreSQL` → one canonical skill). Word-boundary
matching: `R` does not match "Requirements"; `Go` does not match "Google"; `C` does not match
"C++" as a false positive. Required vs preferred split from cues. Fallback to all-required
sets `requirement_split_inferred: true`. `"3+ years"`, `"at least 5 years"`, `"minimum of two
years"` → the right ordinal. `"Bachelor's degree"` → `bachelor`. Boilerplate ("equal
opportunity employer") excluded from keywords. An empty and a 200-char minimal JD do not
raise.

### `analyzers/scorer` (Phase 8) — the most important unit tests
| Test | Asserts |
|---|---|
| Weight sum | The weight constants sum to exactly 100 |
| Arithmetic | `overall_score == round(sum(points_earned))` |
| Bounds | `0 <= points_earned <= points_possible` for all eight categories |
| Determinism | Two identical calls produce identical output |
| Purity | Passing a frozen input twice mutates nothing |
| Perfect match | A résumé containing every requirement scores ≥ 90 |
| No match | An unrelated résumé scores low but never below 0 |
| No required skills in JD | `points_possible == 0`, other categories rescale to 100, no `ZeroDivisionError` |
| No preferred skills in JD | Same rescaling behaviour |
| Partial credit | A related-skill match earns exactly 0.5 units |
| Keyword cap | 60 % coverage earns full marks; 100 % earns the same |
| Missing dates | Experience scores the neutral 4, not 0 |
| Populated fields | Every category has non-empty `explanation`, `evidence`, `limitation` |
| Worked example | The example in `06-scoring-methodology.md` reproduces to 69 |

That last test keeps the documentation honest: if the code changes, the documented example
fails.

### `security/` (Phase 4)
bcrypt hash ≠ plaintext and verifies correctly; a wrong password fails; the same password
hashes to different values (salting); JWT round-trip; expired token rejected; wrong-secret
token rejected; `alg: none` rejected; refresh token is stored hashed; a revoked token fails.

## 3. API integration tests (FastAPI `TestClient`)

Run against a real PostgreSQL test database in a transaction rolled back per test. **Not
SQLite** — the schema uses `CITEXT`, JSONB, and cascade behaviour that SQLite does not
reproduce, and testing against a different engine than production is a false signal.

Auth: register success · duplicate email 409 · weak password 422 · login success · wrong
password 401 · unknown email 401 (identical body) · `/auth/me` with and without a token ·
expired token 401 · refresh success · refresh after logout 401 · rate limit 429.

Analyses: create with a valid PDF + JD 201 · missing file 422 · wrong type 415 · oversized
413 · scanned PDF 422 with the right code · short JD 422 · list paginated · get own 200 ·
**get another user's 404** · **patch another user's 404** · **delete another user's 404** ·
delete own 204 then get 404 · stats with zero analyses returns zeros not 404.

AI behaviour: with `AI_API_KEY` unset the analysis returns 201 with
`ai_status: "unavailable"` and `ai_reason_code: "not_configured"` · a mocked timeout returns
201 with `reason_code: "timeout"` · a mocked malformed response returns 201 with
`invalid_output` · a mocked success attaches AI recommendations with `source: "ai"`.

Failure modes: a mocked database error returns 500 with the generic envelope and no trace ·
a disallowed CORS origin receives no allow header · the error body of a forced exception
contains no path or exception class name.

## 4. Frontend tests (Vitest + React Testing Library)

Queries use accessible roles and labels (`getByRole`, `getByLabelText`) rather than test IDs —
so a test that passes is also evidence the element is reachable by assistive technology.

| Component | Tests |
|---|---|
| `LoginForm` | Renders labelled fields · invalid email shows an error · submits on valid input · shows the server error message · disables the button while submitting |
| `RegisterForm` | Password rule enforced client-side · mismatch error · success redirects |
| `FileUpload` | Accepts a PDF · rejects a non-PDF with a message · shows name and size · clear button resets · drop zone is keyboard-operable and announces its state |
| `ScoreBreakdown` | Renders all eight categories · shows weight and earned/possible · expands to show evidence · renders the disclaimer |
| `SkillList` | Groups matched/partial/missing · empty state when a group is empty · counts are correct |
| `AnalysisHistoryTable` | Renders rows · empty state for a new user · skeleton while loading · error state with retry |
| `DashboardStats` | Formats numbers · handles zero analyses · chart shows an explanatory empty state below 2 points |
| `ProtectedRoute` | Redirects when unauthenticated · renders children when authenticated · no login flash while auth resolves |
| `Modal` | Traps focus · closes on Escape · returns focus to the trigger · has `role="dialog"` and `aria-modal` |
| `ErrorBoundary` | Renders a fallback and does not blank the page |

API modules are tested with a mocked axios instance: the 401 interceptor refreshes once and
retries, and logs out on a second failure.

## 5. Manual testing checklist (Phase 13)

**Cross-browser:** Chrome, Firefox, Edge — full flow on each.
**Responsive:** 360 px, 768 px, 1024 px, 1440 px — no horizontal scroll, no overlap, sidebar
becomes a drawer below 1024 px, tap targets ≥ 44 px.
**Keyboard only (no mouse):** reach and operate every control on all twelve pages; focus
visible at every step; modal traps and restores focus; skip-to-content link works.
**Screen reader spot check (NVDA):** form errors announced; the analysis-complete status
announced via a live region; images have alternative text; heading order is logical.
**Reduced motion:** with the OS setting enabled, transitions are suppressed.
**Error paths, by hand:** stop the API and submit a form · upload a 20 MB file · upload a
scanned résumé · paste a 50-char JD · let a token expire and act · load `/analyses/<random
uuid>` · visit an unknown route.
**Print:** results page prints without navigation, is legible in black and white, and retains
the disclaimer.
**Data:** register a fresh account and confirm every empty state · delete an analysis and
confirm it is gone from history and from the dashboard aggregates · delete the account and
confirm login then fails.

## 6. Tooling and CI

Backend: `pytest`, `pytest-cov`, `pytest-asyncio`, `httpx`, `factory-boy`.
Frontend: `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom`,
`@axe-core/react` for the accessibility pass.

```yaml
# .github/workflows/ci.yml — Phase 2
on: [push, pull_request]
jobs:
  backend:   # postgres service container → pip install → ruff → pytest --cov (fail under 80)
  frontend:  # npm ci → tsc --noEmit → eslint → vitest run → npm run build
  security:  # pip-audit → npm audit --audit-level=high
```

A red build blocks merge. Every feature branch opens a pull request even though the repository
has one contributor — the PR is where the reasoning is recorded, and reviewers of the
portfolio read PRs.

## 7. Test data policy

All fixtures are **fictional and labelled as such**. Résumé fixtures are generated by a
committed script; job description fixtures are paraphrased, not copied from real postings.
No real person's résumé, no real email address, and no real company's proprietary text
appears anywhere in the repository (see `07-security-privacy.md` §3).
